# meeting-notes-expert

把会议录音转写、访谈、播客、讲座整理成结构化纪要的 AI 技能。适用于 Claude / ZCode / Codex / Cursor 等任意 SKILL.md 体系。

它和「让模型总结一下这段会议」的区别在于：结构不是固定的章节表,而是先判会议性质再决定取舍；没有内容的章节整节删除,不留占位句；待办要区分谁真的认领了、谁只是随口一提；出稿后有机器校验,不只靠模型自觉。

## 核心设计

### 会议性质决定结构

出稿前先判这场会要产出什么,判定结论写进基本信息区的「会议性质」字段——它是读者理解「这份纪要为什么长这样」的第一依据。

| 性质 | 判据 | 结构侧重 |
| --- | --- | --- |
| 决策审批 | 有明确拍板、表决、批准 | 结论 → 关键决策 → 风险与顾虑 → 待办 → 内容 |
| 工作推进 | 汇报进展、分工、排期 | 结论 → 待办 → 时间线 → 待定 → 内容 |
| 研讨交流 | 交换意见、讨论方向,无拍板 | 结论 → 分歧与转折条件 → 待定 → 内容(通常无决策节) |
| 汇报通报 | 单向信息传递,无讨论无任务 | 结论 → 内容 |

混合性质按主要目的判一条,不写「兼有」。

### 章节计划是上限不是配额

每个模板列出的章节是「这场会最多需要写到什么」,不是「每节必须填点什么」。某节没有实质内容就整节删除,不留标题、不写占位句。

留一个空标题等于暗示「这里该有内容」,模型于是会从模糊表述里造出决议与任务。宁可少一节,不要造一条。

这条规则的代价是:删掉决策节之后,读者分不清「确认过没有决策」和「漏写了决策」。所以「会议结论」首段必须明确写出本次未形成决议,这是唯一的区分依据。

### 待办分四类,不是两类

会上说话分四种,落到四个不同位置:

| 类型 | 判据 | 落到哪 |
| --- | --- | --- |
| 行动项 | 有承接人 + 明确动作 + 确定承诺 | 待办事项表 |
| 软承诺 | 有承接人,但说「尽量」「看看能不能」「有空时」 | 待办事项表,优先级低,备注标「强度：软性」 |
| 无人认领 | 提出了该做,但没有任何人承接 | 无人认领事项节 |
| 开放问题 | 未决疑问,无承接动作 | 待定与开放问题 |

判别真行动的关键只有一条:这句话里能不能找出一个具体人名或「我／你＋姓名」。找不出就是孤儿,不是行动项。

「应该有人去问下口径」「回头得找个人盯一下」「大家会后跟进」都进无人认领节——让人决定指派还是放弃,而不是塞进待办表把「待定责任人」的行数刷高。

### 六类骨架

判定凭材料性质,不凭文件名。一场「访谈」若以决策为目标就按会议出稿;一次「会议」若是纯分享无决议,按讲座出稿更合适。

| 类型 | 判据 | 骨架 |
| --- | --- | --- |
| 会议·常规 | 多方,以达成决策或分工为目标 | 必填两节 + 条件节 |
| 会议·正式 | 董事／股东／委员会,纪要具法律效力,有表决 | 常规 + 法定要素节 + 审批脚注 |
| 会议·复盘 | 回顾一段工作,产出改进项而非任务 | 四节(目标结果／做得好／待改进／下轮改进项) |
| 会议·站会 | 一刻钟内的进度同步,无决策 | 三节(进度／计划／阻塞) |
| 通用(访谈／播客／讲座) | 信息主要在讲者一侧 | 通用骨架 + 专属节(原话／时间戳／术语定义) |
| 完整分层版 | 需要逐条给出判断依据的重型评审 | 七章两级结构 |

会议亚型(一对一／冲刺计划／产品评审／干系人同步)在常规之上追加特定节,不换整套模板。

### 四个带前提的维度

这四个节吸纳自成熟实践,但都不是无脑加——每节有触发条件,不满足就不出:

- **风险与顾虑**:会上出现明确风险判断、顾虑、反对意见或「一旦××就麻烦」类表述时设
- **时间线**:截止日期或多条里程碑分散在不同议题时设
- **分歧与转折条件**:出现明确立场对立,且有人给出条件性表述时设。写法固定两段——分歧是什么、各方立场,以及什么证据能让他们改变立场
- **无人认领事项**:出现「应该有人去××」这类提出但没人认领的事时设

研讨交流型会议最该有的是「分歧与转折条件」,比孤立列分歧有用得多。

## 机器校验

模型写完不等于写对。`validate_minutes.py` 把能机检的项目全部下沉成断言,出稿后跑一遍:

```bash
python "$MNX_SCRIPTS/validate_minutes.py" 纪要-终.docx --source 会议原文.txt
```

检查项包括:

- **结构**:必需节齐备、待办表七列、状态枚举合法、基本信息区不得是表格
- **文风**:不得出现「待确认／存疑／转写亦作」等标注,决策不得写成「讨论了…」
- **溯源**(给了源材料才做):成稿里的每个数字都必须在原文出现;日期要么原文出现过要么能由会议时间换算;待办责任人必须在原文出现;备注里的出处锚点必须能在原文定位
- **说话人归属**:出处引文能定位到某段而该段说话人与责任人不是同一人时提示(可能是代派或跨段发言)
- **章节名**:二级标题不在模板表内时报出来——自创章节名会让整节内容不进任何校验,这是最隐蔽的失效形态

输出三态:`complete` 全过、`degraded` 无 FAIL 但有 WARN、`failed` 有 FAIL。

溯源核对里有两个不显而易见的设计:数字比对要把中文数字也展开(「两万亿」写成「2 万亿」不能算编造);时间戳要先剥掉,否则原文的 `[00:12]` 会给编造的「12 台」背书。

## 安装

整个目录放到技能目录下,任选其一:

```
~/.zcode/skills/meeting-notes-expert
~/.agents/skills/meeting-notes-expert
~/.claude/skills/meeting-notes-expert
```

宿主会自动加载。无需编译。

## 依赖

| 依赖 | 用途 | 缺失时 |
| --- | --- | --- |
| Python 3.10+ | 跑 scripts 下的脚本 | 无法出稿校验 |
| `python-docx` | 读写 docx | `fix_minutes_docx.py` 不可用 |
| `pymupdf` | PDF 转 PNG 做渲染目检 | 跳过渲染目检 |
| `jsonschema` | 按 schema 校验导出结构 | 该项降级为 WARN |
| `article-format` 技能 | docx 排版规范 | 只能出 md,无规范 docx |

前三项与 `jsonschema` 见 `requirements.txt`。`article-format` 是另一个独立技能,通过 `AF_SCRIPTS` 环境变量定位其脚本,不假定固定路径。

`validate_minutes.py` 只用标准库就能跑校验与导出,`jsonschema` 缺失时降级为 WARN 而不是报错。

## 用法

出稿分两步:提炼(AI 按 `SKILL.md` 写 md)与出稿(脚本转 docx 并校验)。

```bash
export MNX_SCRIPTS="$HOME/.zcode/skills/meeting-notes-expert/scripts"
export AF_SCRIPTS="$HOME/.agents/skills/article-format/scripts"

cd <纪要工作目录>
python "$AF_SCRIPTS/md2docx.py" 纪要.md 中间.docx --profile formal-doc
python "$AF_SCRIPTS/article_style.py" 中间.docx 纪要.docx --profile formal-doc
python "$MNX_SCRIPTS/fix_minutes_docx.py" 纪要.docx 纪要-终.docx
python "$MNX_SCRIPTS/validate_minutes.py" 纪要-终.docx --source 会议原文.txt
```

`md2docx.py` 的输出只取文件名并强制落在当前工作目录,所以必须先 `cd` 到目标目录。

换文体要改源稿重跑,不要拿成品重排——`article_style.py` 只换样式,已固化的编号与表格版式不会跟着变。

## 结构化导出

纪要到这一步之前只是给人看的文档,下游拿不到任何字段。加 `--export` 转成机器可读 JSON:

```bash
python "$MNX_SCRIPTS/validate_minutes.py" 纪要-终.docx --export 纪要.json
```

导出结构由 `references/minutes-schema.json`(v3)定义,关键字段:

- `document_kind` — 判定出的骨架类型,与校验器共用同一判据
- `action_section` — 本次行动项取自哪一节。会议在「待办事项」、复盘在「下轮改进项」、分层版在「行动项」、通用总结在「行动事项」
- `meeting_type` — 会议性质
- `action_items` — 行动项数组,含责任人、完成时间、优先级、状态、出处锚点、表述强度
- `unclaimed_items` / `risks` / `timeline` / `divergences` — 四个条件节的结构化数组
- `document_status` — 与校验器的三态同源,不会出现「校验 PASS、导出 failed」

四个条件节保持字符串数组,不硬拆成字段。它们的填法本身是自由散文(「什么风险、谁的判断、什么前提」),硬拆会逼出编造。

## 跨会滑期跟踪

「同一件事滑期两次就必须改责任人、改日期或改范围」这条规则写在提取口径里很久了,但一直只能人工自查。加索引之后可以机检:

```bash
python "$MNX_SCRIPTS/validate_minutes.py" 纪要-终.docx \
  --index 纪要索引.jsonl --compare --export 纪要.json
```

`--compare` 会拿本次行动项与索引历史比对,结果写进 `cross_meeting_report`:

- `slipped` — 本次完成时间比上期晚,逐条列出改期前后与累计次数
- `must_act` — 累计滑期 ≥2 且仍未完成,该改人、改期或改范围了
- `vanished` — 上期有、本期没出现也未完成,可能是悄悄丢了

跨会认同一件事靠「责任人 + 事项归一化串」。同一件事换人做算新任务,不算滑期。

## 输出变体

默认交付完整版。按受众派生三种:

- **一页版** — 给未参会的管理层:基本信息 + 结论 + 决策 + 待办 + 待定,删掉会议内容
- **任务清单版** — 贴群或进看板:仅待办,按「@责任人 完成时间 事项」逐行输出
- **会前简报版** — 给决策者的单页:事由、背景、关键考量、所需决策、联系人,控制在一页

另有完整分层版与会前叙事文档两种重型形态,用于需要逐条给出判断依据的评审和方向性会议。

变体的数字与措辞必须与完整版一致,只做删减不做改写。

## 设计取舍

几处刻意简化,以及各自的升级路径:

**不做转写。** 转写归上游管线,本技能只做提炼。理由:转写引擎与硬件、密级、语言强相关,混进来会把技能变成平台绑定。它认识的上游只有一件事——转写产物长什么样(`[mm:ss] 说话人N：` 前缀)。任何生成这种格式的工具都能接上。

**没有稳定任务 ID。** 待办表每次会议重新编号,跨会只能靠内容匹配。所以同一件事换个说法就会被判成新增,原条目被判成消失。要根治得引入会议系列标识,那是跨会状态服务的范畴,不属于一个出稿技能。

**四个条件节不拆字段。** 保持字符串数组。拆成「风险等级／影响面／责任人」这类结构化字段看似更有用,实际会逼模型把模糊表述硬塞进格子,或者编出格子里缺的内容。

**模板示例与规则可能冲突时以规则为准。** 骨架图里的「一、二、三」是说明层级的行文标记,落稿时章节标题不写编号,编号由 Word 自动生成。校验器会剥掉标题前的编号再比对,但没必要给自己制造麻烦。

**只校验能机检的。** 决策是否真的在会上达成、风险判断是否准确、纪要是否抓住了重点,这些判不了。校验器只管结构与溯源,不装作能评判内容质量。

## 自检

```bash
# 校验器内置断言
python "$MNX_SCRIPTS/validate_minutes.py" --selftest

# 全量回归
python -I tests/test_all.py
```

`--selftest` 24 项覆盖必需节、待办列、状态枚举、溯源、未识别章节、编码兜底、骨架导出、跨会滑期。

`tests/test_all.py` 65 项覆盖六类骨架的判定与导出、UTF-8/UTF-8-BOM/GBK/UTF-16 四种编码、五种标题编号前缀、schema 合规、既有校验项不退化、CLI 端到端。

改提炼口径后跑 `--selftest` 确认校验逻辑没退化;改骨架或章节名后跑全量回归。

## 输入格式

直接给文本或文件路径即可。支持的形态:

- 带 `[mm:ss] 说话人N：` 前缀的转写稿(上游管线产物)
- 普通 md / txt / docx 记录
- 手写笔记、聊天记录、散会整理稿

缺失会议基本信息时直接省略该字段,不推测补全。材料开头截断或中途缺失时主动收缩推论强度,不把残缺片段当完整事实展开。
